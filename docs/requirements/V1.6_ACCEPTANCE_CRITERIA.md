# v1.6 acceptance criteria

1. Any role with `content.bulk_upload` sees a contextual bulk-upload action.
2. ZIP traversal, symbolic links, encryption, nested archives, excessive entries, and excessive expansion are rejected.
3. Changed files create new immutable versions; exact duplicates do not overwrite history.
4. Supported formats produce explicit extraction records; unsupported formats do not receive fabricated text.
5. Audio/video are marked transcript-required before indexing.
6. Chunks are deterministic and linked to one document version.
7. Qdrant payloads always include tenant, version, scope, visibility, current-version and deletion flags.
8. Retrieval applies a server-generated tenant filter and PostgreSQL defence-in-depth authorisation.
9. Attached document versions enter the same conversation only after access validation.
10. Institutional and external source cards are genuine retrieval records and unknown citations remain removable by the integrity guard.
11. Prior versions remain auditable with uploader, role, time, checksum, batch and provenance.
12. Document lifecycle transitions are permission-scoped, follow the approved transition graph, and preserve append-only actor/reason history.
13. Document lists, version history and upload-to-existing-document operations enforce owner and organisational-scope access inside the service layer.
14. Owner-machine validation must prove MinIO, PostgreSQL, Qdrant, Ollama embeddings, upload, extraction, retrieval and browser behaviour before release acceptance.
