# v1.8 Acceptance Criteria

## Review-cycle creation

- [ ] A review cycle can only target an output already submitted for review.
- [ ] Each cycle pins the exact current output version.
- [ ] A sealed review pack contains a deterministic manifest checksum.
- [ ] Duplicate assignee entries are rejected.
- [ ] External assignees require an active scoped external grant.

## Assignment-specific access

- [ ] A reviewer cannot read or modify another reviewer's task.
- [ ] An external user's grant is checked for status, time, action and resource on every operation.
- [ ] Grant revocation and expiry prevent subsequent access.
- [ ] The Institution Administrator has no automatic academic decision authority.

## Findings and submissions

- [ ] Findings capture criterion, category, severity, evidence locator, recommendation and blocking status.
- [ ] Only the assigned reviewer can edit a finding before submission.
- [ ] Submitted review evidence is immutable and hashed.
- [ ] The output owner or authorised academic user can respond to findings.
- [ ] Blocking findings require a response before correction resubmission.

## Decisions and correction cycles

- [ ] A formal decision is blocked until all current-round tasks are submitted.
- [ ] Reviewer recommendations do not themselves approve or release an output.
- [ ] Approved, conditional, changes-required and rejected decisions are supported.
- [ ] Corrections create a new output version, review pack, task round and evidence trail.
- [ ] Earlier rounds remain available and unmodified.

## Unified UX

- [ ] Review actions are contextual within the single AI work area.
- [ ] No separate moderation portal or artifact workspace is introduced.
- [ ] Moderators can view assigned tasks, record findings and submit recommendations.
- [ ] Heads of Department can view scoped review oversight summaries.

## Validation

- [ ] Unit and static contract tests pass.
- [ ] Migration, RLS, external expiry, browser and end-to-end tests pass on the owner machine before production claims.
