# v1.4 Acceptance Criteria

## Authentication

- Passwords are Argon2id hashes and never returned.
- Access tokens use a fixed configured algorithm and required claims.
- Refresh tokens are opaque, hashed, rotating, expiring, and revocable.
- Production refuses development headers, exposed invitation tokens, and template JWT secrets.
- Repeated failed login attempts cause a time-limited lock.

## Role independence

- One session activates one role assignment.
- Head of Department cannot use Institution Administrator permissions while signed in as Head of Department.
- Institution Administrator does not automatically receive course-assignment authority.
- Role scope descendants are resolved through the closure table.

## Institution administration

- Administrator can invite, suspend, reactivate, and deactivate tenant memberships.
- Administrator can assign and revoke scoped roles.
- Administrator can define and assign institution position labels.
- Administrator can create and maintain a configurable institutional hierarchy.
- Administrative changes are audited.

## Head of Department

- HOD can assign, reassign, and end lecturer allocations in authorised departments.
- HOD can assign coordinators and moderators within scope.
- Previous assignments are retained.
- Department overview identifies unassigned offerings and workload totals.

## Unified interface

- Role actions open inside the single application shell.
- No separate lesson-plan, rubric, report, or administration application is created.
- Tokens are not stored in localStorage or sessionStorage.
- The interface does not claim AI generation succeeded before v1.5.

## Release condition

Static completion is not production acceptance. Owner-machine validation must pass every item in `docs/operations/V1.4_OWNER_MACHINE_VALIDATION.md`.
