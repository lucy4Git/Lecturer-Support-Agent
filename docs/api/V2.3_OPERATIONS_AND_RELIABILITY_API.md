# v2.3 Operations and Reliability API

All endpoints require a valid active-role session. Operational access is granted only to the independent Institution Administrator role unless an institution later defines a separately audited platform-operator role.

## Durable job endpoints

- `GET /api/v1/operations/jobs` — list tenant jobs, optionally filtered by status.
- `POST /api/v1/operations/jobs` — enqueue an allowlisted durable job.
- `GET /api/v1/operations/summary` — return queued, running, retry, completed, failed, and dead-letter counts.
- `POST /api/v1/operations/dead-letters/{dead_letter_id}/replay` — create one auditable replay job.

## Backup and recovery evidence endpoints

- `GET /api/v1/operations/backups` — list tenant-scoped backup records.
- `POST /api/v1/operations/backups` — create a governed backup request and durable job record.
- `POST /api/v1/operations/backups/{backup_run_id}/restore-drills` — create a non-destructive restore-drill record and durable job request.

The database records and APIs are implemented. The real backup and restore-drill job handlers deliberately fail with `NotImplementedError` until they are connected to the owner-machine or deployment-specific storage and database tooling. PowerShell scripts provide the current explicit operator-controlled backup and restore path.

## Public operational endpoints

- `GET /health` — process liveness only.
- `GET /ready` — dependency-aware readiness; returns HTTP 503 when a required dependency is unavailable.
- `GET /metrics` — Prometheus text metrics. Production requires `X-Metrics-Token` or a Bearer token matching `METRICS_TOKEN`.

## Security rules

- Job types are server allowlisted.
- Tenant ID, requesting user, role, and correlation ID are derived from the authenticated context.
- Payloads must not contain raw secrets.
- Idempotency keys are unique within a tenant.
- Dead-letter replay is one-time and creates a new job rather than mutating the original failure evidence.
- The `lsa_worker` database role is independent, non-superuser, and cannot bypass row-level security.
- Cross-tenant job claiming occurs only through audited `SECURITY DEFINER` functions owned by the migration role; business data access still requires the job tenant context.
