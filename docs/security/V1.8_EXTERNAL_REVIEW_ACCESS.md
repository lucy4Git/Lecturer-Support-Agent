# v1.8 External Review Access Security

## Security objective

An external moderator or reviewer must receive the minimum access necessary to complete one assigned task, for a limited period, with complete audit evidence.

## Required controls

1. **Identity and role:** the authenticated user must hold the active external role assignment.
2. **Exact assignment:** the user must be the `assigned_user_id` on the task.
3. **Tenant boundary:** every row and query carries the active `tenant_id` and remains subject to PostgreSQL row-level security.
4. **Grant state:** the external grant must be active, not revoked, and within its start/expiry window.
5. **Action boundary:** the requested action must appear in `allowed_actions` or an explicitly governed wildcard.
6. **Resource boundary:** at least one exact grant boundary must match; mismatched specified boundaries fail closed. Supported boundaries include review task, review cycle, generated output, output version and module offering.
7. **Version pinning:** the review task targets one immutable output version. Later lecturer edits are not silently substituted.
8. **No approval inheritance:** external reviewers and moderators can submit recommendations and findings but cannot formally approve or release materials.
9. **Revocation:** authorised staff can revoke a grant immediately; later task access fails.
10. **Expiry:** due grants are converted to expired status and recorded through expiry events and audit evidence.

## Threats addressed

- guessed task or output identifiers;
- access to unrelated modules or assessments;
- using an expired invitation or grant;
- reviewing a later version that was not assigned;
- reviewer recommendations being misrepresented as institutional approval;
- data leakage after the review engagement ends;
- cross-tenant access through vector search, object storage or application APIs.

## Owner-machine validation

The static contracts do not replace live testing. Validation must prove grant revocation, expiry, exact-resource matching, tenant isolation and database row-level security with real PostgreSQL sessions.
