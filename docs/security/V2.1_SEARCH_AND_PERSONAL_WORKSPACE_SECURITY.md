# v2.1 Search and Personal Workspace Security

## Threats addressed

- Cross-tenant search leakage.
- Client-side filtering of unauthorised records.
- Guessing document-version, saved-output, or notification identifiers.
- A reviewer searching unrelated assessments.
- A user saving an output version they cannot access.
- Notification disclosure to another user in the same institution.

## Controls

1. Every workspace table contains `tenant_id` and is covered by PostgreSQL row-level security.
2. Governance-schema RLS is explicitly included for notifications.
3. Search executes within the server-generated tenant and active-role context.
4. File candidates pass the existing version-level access service before returning.
5. Review search returns tasks assigned to the current user only.
6. Saved outputs are unique by tenant, user, and immutable output-version identifier.
7. Notification reads and updates require exact recipient-user equality.
8. Search query length is bounded and normalised before use.
9. API keys and provider details are unrelated to workspace search and remain outside the client.

## Known validation dependency

The RLS and identifier-guessing negative cases require a live PostgreSQL owner-machine run. Static implementation is not evidence that the database policy has executed successfully.
