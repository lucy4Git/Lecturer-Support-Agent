# v2.2 Analytics, Audit and Settings Security

## Threats addressed

v2.2 is designed to prevent:

- cross-institution analytics disclosure;
- a lecturer obtaining department-wide or institution-wide metrics;
- Heads of Department inheriting Institution Administrator audit functions;
- external reviewers seeing unrelated activity;
- raw credentials being stored as platform settings;
- restricted content being routed to prohibited cloud providers;
- report or audit-export tampering;
- untraceable configuration changes.

## Defence layers

### Tenant isolation

Every new table is tenant-owned. The migration reapplies the PostgreSQL row-level-security policy framework to the `analytics`, `governance` and `audit` records used by v2.2.

### Scope authorisation

Analytics scope is resolved server-side. Personal roles are always restricted to the active user. Departmental roles must supply an authorised organisational unit. Institution scope is available only to the Institution Administrator.

### Permission separation

- `analytics.read_own`: personal metrics;
- `analytics.read_department`: authorised academic-unit metrics;
- `analytics.read_institution`: tenant-wide metrics;
- `audit.centre.read` and `audit.export`: Institution Administrator only;
- `settings.manage`: Institution Administrator only;
- `ai_governance.manage`: Institution Administrator only.

### AI governance

Before routing, the effective policy may limit providers, require local processing or block a request after a governed threshold. The router receives an allow/deny set rather than trusting client input.

### Secret handling

Platform-setting keys and values are screened for credential markers and known token prefixes. Raw secrets are rejected. A valid secret-backed configuration stores only an environment-variable or secret-manager reference. `.env` remains ignored and excluded from safe archives.

### Integrity and auditability

Report runs and audit exports are hashed using SHA-256. Policy, setting, alert, report and export actions generate audit events with the active role, tenant context and correlation identifier.

## Privacy notes

Personal analytics use the requesting `user_id`; they do not aggregate every user sharing the same role. Cost information is an estimate and must be labelled accordingly. Analytics should not expose student-identifiable data unless a later authorised use case explicitly requires and governs it.

## Pending runtime proof

Live RLS denial tests, database-role grants, migration rollback, concurrent usage-ledger updates and browser role visibility must be proven on the owner machine before acceptance.
