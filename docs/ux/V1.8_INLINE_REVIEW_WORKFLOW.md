# v1.8 Inline Moderation and Review UX

## Single work-area rule

Moderation is not a separate application or portal. Review actions appear contextually in the same commercial AI work area used for conversations, teaching-output editing, source cards, upload and export.

## Output-owner journey

1. The lecturer generates and edits an output in the conversation.
2. The lecturer submits the draft for review.
3. An authorised Head of Department or coordinator selects **Create review cycle** on the same output card.
4. The system assigns an exact version and seals the review pack.
5. Findings and requests for correction are shown against the output workflow.
6. The lecturer edits the output as a new immutable version, responds to findings and resubmits.

## Reviewer journey

The contextual **Review tasks** panel lists only assignments for the active reviewer. The reviewer can accept, start, record evidence-based findings and submit a recommendation. External access is checked on each action.

## Decision-maker journey

The authorised decision-maker sees cycle state, reviewer submissions and blocking findings. The system distinguishes a reviewer recommendation from the final academic decision. Approved material may then follow the v1.7 release controls.

## Departmental oversight

The Head of Department's contextual **Review oversight** action summarises active, pending and overdue work. It does not require leaving the Lecturer Support Agent and does not expose unrelated departments.

## Commercial UX requirements retained

- responsive desktop, tablet and mobile layouts;
- keyboard-operable actions and labelled form controls;
- progress, empty, error and expired-access states;
- clear version, round and status badges;
- no hidden overwrite of outputs, findings or submissions;
- no exposure of provider internals, agent selectors or API credentials.
