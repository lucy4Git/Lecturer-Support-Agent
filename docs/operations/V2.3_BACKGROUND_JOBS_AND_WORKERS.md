# v2.3 Background Jobs and Workers

## Why jobs are durable

Document ingestion, exports, reports, retention, notifications, external-access expiry, and backups must survive browser disconnects and process restarts. PostgreSQL is the source of truth; jobs are claimed using time-limited leases and `FOR UPDATE SKIP LOCKED`, allowing concurrent workers without ordinary duplicate claims.

## Database-role design

The API uses `lsa_app`. The worker uses the independent `lsa_worker` role through `WORKER_DATABASE_URL`. Both roles are non-superusers and cannot bypass row-level security.

A worker must discover jobs from several tenants, so the migration installs narrowly scoped `SECURITY DEFINER` functions for claim and expired-lease recovery. Those functions return one job and its tenant. The worker then establishes that tenant as the active database context before a domain handler accesses tenant-owned business records. This avoids granting the worker unrestricted table access.

## States

`queued → running → completed`

A failure becomes `retry` with exponential backoff. When `max_attempts` is reached it becomes `dead_letter`. An expired worker lease is recoverable and must not silently lose work.

## Start locally

```powershell
.\scripts\operations\Start-BackgroundWorker.ps1
```

Run one claim cycle:

```powershell
.\scripts\operations\Start-BackgroundWorker.ps1 -Once
```

## Handler gate

The registry accepts only allowlisted job types. A domain handler must be wired and integration-tested before its job type is considered operationally complete. Domain handlers that are not connected currently raise `NotImplementedError`; the queue records a retry or dead letter rather than falsely reporting completion.

The durable queue, leases, attempts, retries, and dead-letter evidence are implemented and statically validated. Live cross-tenant claiming, tenant-context application, and domain service execution remain owner-machine validation items.
