# v2.0 Failure Triage and Rollback

## Triage order

1. **Secret or tenant-isolation failure:** stop immediately; do not continue with live data.
2. **Migration or RLS failure:** preserve logs, inspect the failing revision, and use a reversible development rollback only.
3. **MinIO/Qdrant/Redis failure:** confirm container health, ports and `.env` values without printing secrets.
4. **Ollama failure:** verify the service and exact model tags with `ollama list`.
5. **API failure:** inspect redacted API stderr and readiness dependencies.
6. **Web build failure:** fix type errors or server/client boundary problems before browser testing.
7. **Role-preview failure:** treat unexpected actions as an authorisation defect, not a cosmetic issue.
8. **Provider failure:** keep the provider disabled until the adapter and configured model pass a synthetic probe.

## Safe reruns

The validation command creates a new timestamped evidence directory on every run. It does not delete prior evidence. Synthetic seed records use stable identifiers and should remain idempotent.

## Development rollback

Use Alembic downgrade only in the synthetic local database and only after recording the current revision and preserving the failure logs. Never use `Reset-DevelopmentDatabase.ps1` against a shared, pilot or production tenant.

## Correction record

For each failure record: finding ID, severity, affected stage, evidence path, root cause, files changed, corrective test and final result. Claude must audit these records before new feature implementation begins.
